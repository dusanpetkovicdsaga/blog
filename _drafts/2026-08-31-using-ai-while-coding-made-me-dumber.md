I have been using AI while coding for years, almost like a sidekick.
It helped me ship faster, unblock myself quicker, and get through a lot of repetitive work with less friction.

<!--more-->

But over time I noticed something uncomfortable: the more I outsourced to AI, the more dependent I became on it.
And when it was not there, a lot of the skills I had built over the years felt dulled.
Not gone. Just harder to access.

That was the part that bothered me.

## The Hidden Cost

AI is great at accelerating work.
It is also great at quietly making you stop exercising parts of your brain.

If you use it long enough without being intentional, you can end up in a weird place:

- you produce code faster
- you solve shallow problems faster
- you need less effort to get started
- but your own debugging, reasoning, and recall get weaker

The problem is not that AI is bad.
The problem is that it can become a crutch if you let it do too much of the thinking for you.

## The Tools I Kept Reaching For

These are the kinds of things I used AI for most often:

- generating boilerplate
- writing small helpers and utility functions
- refactoring messy code into something cleaner
- explaining unfamiliar libraries or APIs
- drafting tests
- spotting obvious bugs
- rewriting text, docs, and comments

None of that is inherently wrong.
In fact, most of it is useful.
The issue was the pattern, not the tool.

## The Scenarios That Exposed It

I started noticing the weakness in a few situations.

### 1. Starting From Zero

When I had AI available, I often skipped the awkward part where I would normally think through the problem myself.
I would jump straight to prompting.

That felt efficient.
It also meant I was practicing less of the muscle that matters most: framing the problem clearly before touching the keyboard.

### 2. Debugging Without It

When something broke and I could not rely on AI immediately, I felt slower than I should have.
Not because I had forgotten how to debug, but because I had gotten used to being handed the next likely step.

The search space felt bigger when I had to reason from first principles again.

### 3. Reviewing AI-Generated Code

Sometimes the output looked good enough to merge quickly.
That is dangerous.

If you do that often enough, you stop actively evaluating trade-offs and start trusting fluency.
Fluent code is not the same thing as correct code.

### 4. Learning Less Than I Thought

AI can make you feel like you are learning because you are moving fast.
But speed is not the same as retention.

If I let AI explain everything too early, I understood the answer in the moment and forgot it soon after.
That is a bad trade if the goal is to become a stronger engineer.

## How I Decided to Fight It

I did not want to abandon AI.
I wanted to stop using it in a way that made me weaker.

So I changed a few things.

### Think First, Prompt Later

Before asking AI for help, I try to form my own hypothesis.

What is the problem?
What do I think the solution is?
What trade-offs am I missing?

Even a rough answer helps keep me engaged instead of passive.

### Use AI for Acceleration, Not Replacement

I now prefer to use AI after I have already done some work:

- after I have sketched the approach
- after I have identified the bug
- after I have a rough implementation
- after I have formed an opinion

That makes AI an amplifier instead of a substitute.

### Rebuild the Muscle Manually

For important parts of the job, I deliberately avoid shortcuts sometimes.

I write the code myself.
I trace the bug myself.
I read the docs myself.
I do the first pass without asking for help.

That is slower, but it keeps the underlying skill alive.

### Ask Better Questions

Instead of asking AI to "just solve it", I try to ask for:

- a critique of my approach
- edge cases I missed
- alternatives with trade-offs
- a sanity check on my reasoning

That keeps me in the driver’s seat.

## How It Is Going So Far

Better than before.

I am more aware now when I am using AI lazily versus using it well.
I still use it often, but I try not to let it replace the part of the work that actually makes me better.

The surprising part is that the slower approach often makes me faster later.
When I understand the code more deeply, I spend less time being confused, less time guessing, and less time relying on the model for every small decision.

So no, I do not think AI is making developers worse by default.
But I do think it can make you weaker if you let it do all the thinking.

And I think that is something worth paying attention to.
